# OpenArt 与 RT1021 通信协议文档设计

## 执行状态

- 状态: Archive


## 背景

`Protocol.md` 现有内容主要描述底盘遥控协议,但没有把当前重构后的视觉链路边界单独讲清楚。随着状态机、动作编排和 `?lock/?pos` 同步逻辑逐步迁到 RT1021 端,OpenArt 端后续应从“主动发控制命令”收敛为“提供视觉观测 + 按需查询诊断”。因此需要重写协议文档,帮助 vision 端继续重构。

## 目标

1. 明确当前 OpenArt 与 RT1021 之间的实际串口传输约定。
2. 将协议拆成两个模块:
   - 车模控制协议（遥控协议）
   - 车模与视觉端通信协议
3. 解释视觉专用 `x,y` 上报与传统 `x/y` 绝对位置命令之间的边界。
4. 给出兼容与迁移说明,使 OpenArt 端能据此继续删减旧控制逻辑。

## 非目标

- 不重新定义底盘内部控制算法、状态机阈值或推行策略。
- 不扩展新的视觉字段（如颜色、置信度、角点、类别等）。
- 不描述尚未在当前代码中落地的未来协议。

## 设计决策

### 1. 先写共享传输约定,再分模块说明

- 在两个模块前增加一节“共享传输约定”。
- 统一说明串口角色、波特率、行分帧、查询回写规则和大小写容忍度。
- 避免在遥控协议和视觉协议中重复解释底层串口事实。

### 2. 车模控制协议继续作为兼容外部 API

- 保留 `key=value` 聚合命令格式。
- 保留 `?pos`、`?lock` 等旧查询,并补充 `?vision`、`?health`、`?tick`、`?imu`、`?enc`、`?motor` 等诊断接口。
- 明确哪些命令会触发 `command_lock`,哪些命令在锁定状态会被忽略。

### 3. 视觉协议单独定义为“视觉观测上报”而不是“动作命令”

- 视觉上报只接受 `UART6` 上“恰好只含 `x` 与 `y` 两个键”的单行文本。
- 该 `x,y` 表示图像坐标观测,不是世界坐标绝对位置命令。
- RT1021 仅缓存最新一帧视觉观测,不做排队,超时后视为丢目标。
- 文档中要强调: 如果帧格式不满足视觉协议条件,则仍会落回遥控协议解析流程。

### 4. 兼容与迁移说明必须显式写出“同名字段不同语义”

- `x`、`y` 在遥控协议中表示世界坐标目标（米）。
- `x`、`y` 在视觉协议中表示图像平面目标点（像素）。
- 两者的区分条件不是字段名本身,而是“串口来源 + 帧格式”。
- 这是 OpenArt 端继续重构时最容易踩坑的歧义点,必须单列说明。

## 文档结构

1. 文档目的
2. 共享传输约定
3. 模块 A：车模控制协议（遥控协议）
4. 模块 B：车模与视觉端通信协议
5. 兼容与迁移说明
6. OpenArt 端建议接入方式

## 验收标准

- `Protocol.md` 能直接回答“当前实际协议是什么”。
- 文档能明确区分遥控协议与视觉协议的 `x/y` 语义。
- 文档能指导 OpenArt 端改为“持续发送视觉观测,不再逐帧 `send_cmd_sync()`”。
- 所有关键事实都能追溯到当前 Vision 仓库或 TransportCar 仓库实现。
