# OpenART 纯视觉持续回传重写设计

## 背景

`SmartCar2026-Vision` 当前已经部分转向“纯视觉观测上报”，但仓库内仍残留旧阶段口径，例如轮询、视觉侧控制链路、状态机编排与兼容命令描述。这些旧口径与当前主仓库已经定型的协议主线不一致，容易在后续联调和维护中把实现重新带回历史路径。

当前主线已经明确：视觉端不再承担控制与轮询职责，而是通过固定串口持续直接回传观测；车端主动接收，并根据超时和新鲜度自行判断目标是否丢失。因此，本次改动不做兼容迁移，而是按当前协议整体重写视觉仓库的运行时主文件。

## 目标

1. 将 `main.py` 收口为单文件纯视觉持续回传程序。
2. 保留现有可调参数入口，包括串口、波特率、曝光、发送周期和颜色阈值。
3. 严格对齐当前协议语义，只输出当前主线允许的视觉观测内容。
4. 明确删除旧轮询、旧控制、旧状态机、旧兼容说明对应的实现痕迹。
5. 让主机侧测试能够稳定约束“无历史兼容”的新边界。

## 非目标

1. 不保留任何历史兼容分支。
2. 不在视觉端继续保留动作控制、查询同步或任务状态机。
3. 不把仓库重构成多文件结构。
4. 不扩展当前协议之外的新字段、新查询或新运行模式。

## 设计原则

1. 单文件结构保持不变，运行时唯一入口仍为 `main.py`。
2. 参数集中放在文件顶部，便于现场调整。
3. 逻辑按“参数区 -> 纯工具函数 -> 主循环”组织，降低阅读和联调成本。
4. 只保留对当前比赛主线有直接价值的能力，不为历史路径保留兜底逻辑。
5. 无目标时保持静默，由车端超时机制处理丢失语义，视觉端不发送伪帧。
6. 除观测帧外，唯一允许保留的协议动作是启动阶段可选的一次 `reset=1`；除此之外不得再发送任何非观测文本。

## 运行时职责边界

重写后的 `main.py` 只承担以下职责：

1. 初始化摄像头。
2. 初始化视觉输出串口。
3. 在启动阶段按配置决定是否发送一次 `reset=1`。
4. 基于既有阈值持续检测候选目标。
5. 在每帧候选中选择当前最值得上报的一个目标。
6. 将该目标编码为当前协议要求的观测文本并发送。

重写后的 `main.py` 明确不再承担以下职责：

1. 发送任何离散动作命令。
2. 执行轮询式查询或同步等待。
3. 在视觉端维护控制状态机。
4. 输出任何历史格式的兼容载荷。

## 协议设计落点

### 串口语义

视觉端固定走当前主线视觉链路，使用固定串口和波特率持续输出观测。运行时不再引入查询-应答式交互，也不再将视觉端视作控制端。

### 发送策略

1. 启动完成后，若启动复位开关打开，则发送一次 `reset=1`。
2. 主循环每次抓图后都尝试提取候选目标。
3. 若当前帧无候选目标，则本轮不发送任何观测。
4. 若存在候选目标，则根据发送周期节流发送最新观测。

这里保留一次启动复位，不视为历史兼容，因为它仍属于当前正式协议允许的运行态复位动作；它的目的仅是让车端启动后进入干净状态，而不是恢复旧轮询机制。该动作必须同时满足两个硬约束：只允许出现在启动阶段；整个运行周期最多发送一次。若后续确认现场不再需要该动作，则应整体删除，而不是扩展成其他控制语义。

### 观测内容

发送内容只保留当前协议要求的识别框观测，不保留旧的点坐标格式，不保留旧的控制字段，也不保留任何“为了兼容旧车端”的混合输出。

## 坐标与目标选择

### 坐标归一化

视觉端内部统一将识别框转换到当前协议语义要求的坐标系。该归一化在视觉端固定完成，车端不再承担二次补偿责任。

### 候选选择

候选目标仍基于现有颜色阈值提取。选择规则写死为确定性单规则：在归一化后的协议坐标上，按“横向离画面中心的平方距离 + 纵向离地板侧的平方距离”升序选择；若分值相同，则保留 `find_blobs()` 返回顺序中的第一个候选。除这条规则外，不再保留任何旧阶段的隐含优先级或额外筛选条件，避免实现时把历史逻辑顺手带回。

## 文件结构设计

`main.py` 内部重排为三个区块：

1. 参数区：串口参数、曝光参数、发送周期、颜色阈值、启动复位开关。
2. 工具函数区：识别框转换、坐标归一化、候选构建、候选选择、发送节流、串口写入。
3. 主循环区：初始化、抓图、检测、选择、发送。

这样既维持单文件，又能把“协议处理”和“硬件循环”之间的关系说清楚。

## 测试策略

本次改动严格按 TDD 执行。

### 先写失败测试

先补或更新以下测试，让它们在重写前失败：

1. `main.py` 不允许出现旧轮询、旧查询和旧控制链路痕迹。
2. `main.py` 的观测格式必须严格对齐当前协议。
3. 无目标时不得输出伪帧。
4. 坐标归一化必须在视觉端内部完成。
5. 启动复位行为若开启，只允许在启动阶段发送一次当前协议认可的复位文本。
6. 发送周期节流必须满足边界时刻判定，不得早发或漏发。
7. 运行时不得保留任何查询-应答入口或等待式同步入口。
8. 目标选择必须同时覆盖“分值更小者优先”和“同分时按原候选顺序取第一个”两条规则。

### 再写最小实现

在测试失败被确认后，再重写 `main.py` 的运行逻辑，并补齐使测试通过的最小实现。

### 最后收口文档

将 `README.md` 与 `docs/Protocol.md` 中仍残留的旧轮询、旧控制和旧兼容口径改为当前主线表述，避免仓库文字材料继续误导后续实现。

## 风险与约束

1. 现场阈值、镜像和曝光参数虽然保留，但新的结构重写可能改变代码阅读顺序，因此测试必须先锁定行为而不是依赖旧实现布局。
2. 启动复位若被误写成旧链路控制命令，会把当前纯视觉边界重新打破，因此需由测试明确限定。
3. 文档若不同时更新，后续很容易再次有人把“视觉端兼任控制端”的旧想法带回仓库。

## 验收标准

1. `main.py` 仍为单文件唯一运行入口。
2. 运行时只保留“观测持续回传 + 启动阶段可选一次复位”这两个允许职责。
3. 运行期不存在旧轮询、旧查询、旧控制或旧状态机入口。
4. 仓库内不再宣称旧轮询是当前主机制。
5. 主机侧相关测试通过，并能直接体现“无历史兼容”的边界。
